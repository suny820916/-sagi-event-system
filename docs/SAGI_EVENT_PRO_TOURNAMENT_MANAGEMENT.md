# SAGI EVENT — 专业赛事管理完整能力清单

## 目标

SAGI EVENT 不是简单的“排赛程 + 记比分”工具。

目标是成为：

**可以从报名开始，一直管理到冠军产生、赛后归档的专业足球赛事管理系统。**

基础赛事管理永久免费，但免费不等于简化、阉割、不稳定。

---

# 一、核心对象

系统长期应围绕以下 7 个核心对象设计：

1. 赛事 Event
2. 赛季 Season
3. 球队 Team
4. 球员 Player
5. 比赛 Match
6. 场地 Venue
7. 裁判 Referee

不要把数据全部塞进“比赛”或“球队”对象里。

---

# 二、完整赛事生命周期

专业赛事管理必须覆盖：

报名
→ 审核
→ 球队确认
→ 球员名单
→ 分组
→ 排赛
→ 场地分配
→ 裁判分配
→ 签到
→ 本场名单确认
→ 比赛进行
→ 比分 / 事件
→ 纪律
→ 晋级
→ 冠军
→ 赛后归档
→ 历史数据

---

# 三、P0：优先补齐的专业能力

## 1. 场地管理

系统必须认识“场地”，而不仅仅是比赛时间。

场地至少包含：

- 场地名称
- 场地数量
- 可使用时间
- 不可使用时间
- 场地状态
- 是否允许决赛
- 备注

排赛必须考虑：

- 场地是否可用
- 同一时间是否冲突
- 多场地同时排赛
- 某些比赛只能安排指定场地
- 场地临时关闭后的重新排赛

---

## 2. 智能排赛约束

自动排赛不能只根据球队数量。

必须逐步支持：

- 比赛开始时间
- 单场比赛时长
- 中场 / 间隔时间
- 场地数量
- 最短休息时间
- 最大连续比赛限制
- 避免背靠背
- 多场地冲突
- 指定球队不可比赛时间
- 教练同时带多队时避免同时比赛
- 淘汰赛必须等待前置比赛结果
- 跨场地移动时间（后续）

系统不能静默生成明显不合理的赛程。

遇到冲突，要告诉组织者冲突原因。

---

## 3. 比赛状态系统

比赛不能只有：

未开始
已结束

至少要支持：

- 未排期
- 已排期
- 即将开始
- 进行中
- 中场
- 已结束
- 延期
- 取消
- 中断
- 弃权
- 待确认
- 重赛（需要时）

每种状态必须影响：

- 公开页面
- 积分计算
- 晋级计算
- 通知
- 是否允许修改比分
- 是否允许重新排期

---

## 4. 异常比赛处理

专业赛事一定要处理异常情况。

必须支持：

### 弃权
不能简单把比分写成 0:3。

应记录：

- 比赛结果类型：弃权
- 判定比分
- 弃权球队
- 原因
- 是否影响积分 / 净胜球
- 管理员备注

### 延期
记录：

- 原时间
- 新时间
- 原因

### 取消
记录原因，不应删除历史。

### 中断
比赛中断后可：

- 恢复
- 改期继续
- 判定结果
- 重赛

不要通过“删除比赛”解决异常。

---

## 5. 操作日志 / 审计记录

所有关键赛事数据修改都要可追溯。

至少记录：

- 谁修改
- 什么时候修改
- 修改对象
- 原值
- 新值
- 修改原因（关键操作）

例如：

14:32
管理员A
塔城 vs 托里
比分 1:0 → 1:1

这是专业赛事系统非常重要的安全能力。

未来应支持必要的回滚 / 撤销。

---

## 6. 数据安全与回滚

必须继续强化：

- 自动保存
- 刷新恢复
- 关闭页面后恢复
- 破坏性操作二次确认
- 已有赛果时禁止误重建
- 备份赛事
- 恢复赛事
- 数据版本 / 回滚能力（逐步实现）

稳定优先于动画。

---

# 四、P1：赛事运营层

## 7. 报名管理

球队报名应有状态：

- 已提交
- 待审核
- 审核通过
- 候补
- 拒绝
- 已确认参赛
- 已退出

不能只有“报名 / 未报名”。

---

## 8. 球队签到

比赛当天支持：

- 球队签到
- 领队确认
- 队服确认
- 球员名单确认
- 资格确认
- 队长确认

签到完成后，赛事管理员可标记：

**允许参赛**

---

## 9. 球员名单管理

球队必须支持球员名单。

球员基础信息可包括：

- player_id
- 姓名
- 照片
- 出生年份
- 位置
- 惯用脚（可选）
- 备注

赛事报名关系包含：

- 所属球队
- 球衣号码
- 是否门将
- 是否队长
- 是否可参赛
- 资格审核状态

注意：

“球员是谁”和“这次赛事代表哪支球队”必须分开。

---

## 10. 球员资格管理

逐步支持：

- 年龄组资格
- 重复报名
- 同一赛事跨队报名
- 名单锁定
- 临时替换
- 资格审核结果

敏感信息必须和公开资料分离。

身份证号、证件照片、联系电话、监护人信息等不得公开。

如果只需要确认资格，优先保存：

“资格已验证”

而不是长期保存完整敏感证件。

---

## 11. 本场名单 / 名单锁定

每场比赛前：

球队提交本场名单。

支持：

- 首发
- 替补
- 门将
- 队长

比赛开始后：

默认锁定名单。

如果管理员强制修改：

必须写入操作日志。

---

## 12. 裁判管理

系统需要支持：

- 裁判档案
- 主裁
- 助理裁判
- 第四官员 / 记录员（可选）
- 每场裁判指派
- 裁判时间冲突
- 裁判连续执法提醒

裁判也应该有自己的赛事日程。

---

## 13. 纪律系统

红黄牌不能只是一个比赛动画。

必须进入正式赛事数据。

支持：

- 单场黄牌
- 单场红牌
- 黄牌累计
- 自动停赛提醒
- 红牌停赛
- 追加处罚
- 纪律说明
- 是否跨轮次 / 跨分站有效（赛事规则决定）

系统必须能够回答：

“这个球员下一场能不能上？”

---

## 14. 申诉 / 纠错

逐步支持：

- 比分申诉
- 球员资格申诉
- 纪律申诉
- 管理员裁定
- 裁定记录

不要只修改最终结果，不保留过程。

---

## 15. 赛事角色与权限

未来必须区分：

- 超级管理员
- 赛事管理员
- 分站管理员
- 裁判
- 球队领队
- 记录员
- 公开只读用户

不同角色拥有不同修改权限。

不能所有人都能改比分 / 名单 / 赛程。

---

# 五、比赛现场数据

## 16. 比赛事件时间线

每场比赛应支持事件：

- 进球
- 助攻
- 黄牌
- 红牌
- 换人
- 点球
- 乌龙球
- MVP（赛后）
- 其他自定义事件（后续）

自动形成：

12' 黄牌 · 8号
24' 进球 · 10号
31' 换人
42' 进球 · 7号
FT 2–1

同一份事件数据可被：

- SAGI EVENT 比赛报告
- SAGI BROADCAST 图文包装
- 赛后海报
- 球员个人数据

共同使用。

不要重复录入。

---

# 六、个人数据 / SAGI PLAYER

个人数据应该接入。

但当前不要强制球员注册账号。

第一阶段先建立：

**球员档案 + 赛事报名关系 + 比赛数据**

每个球员拥有稳定内部：

player_id

号码、球队、赛事会改变，但 player_id 不变。

长期可以形成：

- 出场
- 首发
- 进球
- 助攻
- 黄牌
- 红牌
- MVP
- 冠军
- 参加过的赛事
- 参加过的球队

以后可以形成：

SAGI PLAYER / 球员足球档案

这是后续能力，不要在 P0 阶段抢占稳定性开发资源。

---

# 七、通知与沟通

赛事管理最耗精力的事情之一是通知。

逐步支持生成：

- 报名确认
- 赛程发布
- 时间变更
- 场地变更
- 下一场提醒
- 晋级通知
- 纪律停赛提醒

优先考虑中国实际使用场景：

一键生成可以直接转发微信群的文本 / 卡片。

例如：

【比赛提醒】
TARLAN FC
下一场：17:20
对阵：托里青年
场地：1号场
请提前30分钟签到

不需要一开始就开发复杂即时聊天系统。

---

# 八、公开赛事页

管理端和公开端必须分开。

管理端：
可以修改。

公开端：
只读。

公开页可展示：

- 赛事信息
- 赛程
- 实时比分
- 比赛状态
- 积分榜
- 晋级
- 射手榜
- 纪律信息（适当）
- 冠军
- 比赛报告

---

# 九、赛事归档

赛事结束后不能只是留在 localStorage。

长期应形成：

- 历届赛事
- 历届球队
- 历届冠军
- 比赛结果
- 球员数据
- 纪律记录
- 赛事照片 / 媒体关联

特别是 TORANHE CUP：

每一站冠军、年度总冠军和赛事历史必须长期保存。

---

# 十、数据统计

后续支持：

- 射手榜
- 助攻榜
- 黄牌榜
- 红牌榜
- MVP
- 球队进球
- 球队失球
- 净胜球
- 连胜
- 不败
- 零封
- 历史交锋（更后期）

不要在核心赛事稳定前过度扩展统计。

---

# 十一、动态分组仍然是基础要求

分组不能固定 A/B 两组。

球队数量和分组数量独立。

支持：

- 两组
- 三组
- 四组
- 未来更多

支持不等量分组。

支持不同晋级方式。

系统必须根据：

球队数量
+ 分组数量
+ 晋级规则

生成正确赛程和淘汰结构。

# 十三、开发原则

不要一次性实现全部功能。

先建立正确的数据结构。

每增加一个模块：

1. 不破坏旧赛事
2. 不破坏已有比分
3. 不破坏积分 / 晋级
4. 手机端可用
5. 有数据迁移方案
6. 有自检
7. 有异常情况测试

核心原则：

**专业不是功能多，而是正常情况简单，异常情况也能处理。**

以及：

**SAGI EVENT 应该适应真实赛事，而不是让真实赛事迁就系统。**
