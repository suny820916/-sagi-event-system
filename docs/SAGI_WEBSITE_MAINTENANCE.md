# SAGI SPORTS 网站日常维护规范

## 目的

SAGI SPORTS 官网不是一次性项目。

网站需要持续保持：
- 内容准确
- 链接有效
- 手机端正常
- 线上版本与 GitHub 一致
- SAGI 品牌统一
- 不出现过期文案
- 不因新功能破坏旧页面

本规范适用于：
- SAGI SPORTS 首页
- SAGI KIT
- SAGI EVENT
- TORANHE CUP
- SAGI BROADCAST
- ABOUT
- 未来新增公开页面

## 一、每次开始工作的固定检查

Codex 每次进入网站项目，先读取：
- AGENTS.md
- 本文件
- 当前 main 最新提交
- 与本次任务相关的产品文档 / Issue

然后先检查：

1. 首页是否正常打开
2. 主导航是否正常
3. 手机端 390px 是否出现换行、溢出、遮挡
4. 主要页面是否存在 404 / 死链
5. 页面 Logo 是否使用官方 SAGI Logo
6. 是否存在已经过期的产品说明
7. 是否存在“固定8队”“旧版本号”“旧入口”等失效文案
8. 页面按钮是否指向正确产品
9. 本地代码与线上页面是否一致
10. 如无法验证线上，必须明确说明

## 二、日常维护范围

### 1. 内容维护
持续检查：
- 过期文案
- 错别字
- 错误球队名 / 赛事名
- 旧日期
- 旧版本描述
- 已经变化的产品能力
- 未确认信息
- 重复内容

原则：
- 不自行编造赛事结果、冠军、日期
- 未确认内容不得写成正式事实
- 已确认信息优先从结构化数据读取

### 2. 导航维护
主导航保持统一：
- 首页
- 球队装备
- 赛事
- 托朗戈杯
- 直播
- 关于我们

要求：
- 所有主页面导航一致
- 当前页面正确高亮
- 手机端保持单行或合理横向滚动
- 不允许因增加栏目造成两行挤压

### 3. 手机端维护
SAGI 网站以手机端为第一优先。

每次重要修改至少检查：
- 390px
- 430px

重点：
- 导航
- 卡片
- 表格
- 弹窗
- 文件上传
- 打印入口
- 长中文
- 底部固定栏
- iPhone Safari 安全区域

### 4. 链接 / 入口维护
定期检查：
- 主导航
- 首页业务入口
- TORANHE
- EVENT
- KIT
- BROADCAST
- ABOUT
- PDF / 文件
- 分享页

任何 404、错误跳转、旧路径必须修复。

### 5. 品牌一致性
统一使用官方 SAGI FOOTBALL Logo。

保持：
- 黑
- 白
- SAGI 红
- 简洁
- 克制
- 国际足球品牌感

禁止：
- 随意重绘 Logo
- 廉价渐变
- 过度发光
- 无意义动效
- 与品牌不一致的字体/装饰

### 6. 页面性能
避免：
- 巨大图片直接加载
- 不必要 JS
- 重复 CSS
- 无意义第三方依赖
- 首屏阻塞

图片尽量：
- WebP / AVIF
- 合理尺寸
- 懒加载

### 7. 数据与兼容
修改 EVENT / TORANHE 等有数据的页面时：
- 保留旧数据兼容
- 保留备份/恢复
- 不静默丢数据
- schema 变化要有迁移
- 不把大视频/照片直接塞进 Git

### 8. 缓存
更新公共 CSS/JS 后：
- 必要时更新资源版本号
- 避免用户手机继续读取旧缓存

但不要无意义频繁改版本。

### 9. 线上验证
GitHub commit != 线上完成。

每次发布后尽量验证：
- 首页
- 修改页面
- 手机端
- 关键按钮
- 新资源
- 404

如果不能验证线上：
必须写：
“代码已提交，线上部署尚未验证。”

### 10. 安全
禁止把：
- 密钥
- 私钥
- 管理员口令
- 数据库 service key
- 敏感用户信息

写进前端或 GitHub 公共代码。

## 三、每次新功能完成后的回归检查

至少检查：

- 首页
- 导航
- KIT
- EVENT
- TORANHE
- BROADCAST
- ABOUT
- 手机端 390px
- 桌面端
- 主要链接
- Logo
- 底部文案
- 404
- Console 明显错误
- 旧入口

如果修改 EVENT：
额外执行 EVENT 自己的回归测试。

## 四、日常维护不等于乱改

Codex 不允许：

- 为了“优化”随意改品牌文案
- 未经要求重做整个首页
- 把稳定页面重构成新框架
- 因代码洁癖大规模重写
- 擅自删除历史内容
- 擅自改变产品名称
- 擅自合并 TORANHE 与 SAGI EVENT

维护原则：

发现问题 → 判断影响 → 最小修复 → 验证 → 提交。

## 五、维护报告格式

每次维护结束只需报告：

1. 发现的问题
2. 修复的问题
3. 修改文件
4. 手机端检查
5. 线上验证
6. commit
7. 仍需人工确认的事项

不要写大量无关技术过程。

## 六、长期维护重点

持续关注：

- 过期赛事内容
- 过期产品描述
- 导航一致性
- 手机适配
- 死链
- 页面加载速度
- 缓存
- 数据兼容
- GitHub 与线上版本差异
- SAGI 品牌一致性

核心原则：

**网站不是做完一次，而是长期保持正确。**
