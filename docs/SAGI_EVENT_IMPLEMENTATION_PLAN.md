# SAGI EVENT — 专业赛事管理实施计划

## 目标

SAGI EVENT 要从“赛程 + 比分 + 积分工具”升级为可以真正独立完成一届足球赛事管理的专业系统。

核心原则：

- 基础赛事管理永久免费
- 手机优先
- 稳定优先
- 先正确的数据结构，再增加界面
- 不一次性重写整个系统
- 每个阶段完成、测试、提交后，再进入下一阶段
- 旧赛事数据必须继续可用
- SAGI EVENT 应该适应真实赛事，而不是让真实赛事迁就系统

---

# 总体开发顺序

必须按以下顺序推进：

1. 数据模型与规则引擎
2. 球队与球员
3. 本场名单与比赛事件
4. 比赛状态与计时
5. 场地与智能排赛
6. 异常比赛处理
7. 操作日志与回滚
8. 报名 / 审核 / 签到
9. 裁判与纪律
10. 通知与官方比赛报告
11. 公开赛事页
12. 云端历史归档
13. PLAYER / BROADCAST / 媒体联动

不要跳阶段，不要为了展示效果提前做后面的功能。

# M1 — 赛事规则引擎

这是底层能力，不能把比赛规则写死。

至少支持：

## 积分规则
- 胜
- 平
- 负
- 默认 3 / 1 / 0
- 用户可修改

## 小组排名顺序可配置
例如：
- 积分
- 相互战绩
- 相互净胜球
- 总净胜球
- 总进球
- 公平竞赛积分
- 抽签

## 淘汰赛规则
- 常规时间后直接点球
- 加时后点球
- 是否允许重赛
- 自定义特殊规则预留

## 弃权规则
- 判定比分
- 是否计入净胜球
- 是否计入积分
- 是否影响射手等个人数据

验收：
- 同一个赛制在不同规则下能正确算积分和排名
- 规则变更后有明确提示
- 已开始赛事不能无提示改规则

# M2 — 球队与球员管理（当前最高优先级）

## Team
球队至少包含：
- team_id
- 球队名称
- 队徽
- 领队
- 教练
- 联系电话（私有）
- 主场球衣颜色
- 客场球衣颜色
- 门将服颜色
- 备注

## Player
球员基础档案：
- player_id
- 姓名
- 照片（可空）
- 出生年份（可选）
- 位置
- 惯用脚（可选）
- 备注

赛事报名关系：
- team_id
- player_id
- 球衣号码
- 是否门将
- 是否队长
- 是否可参赛
- 资格状态

必须区分：
“球员是谁” 与 “本赛事代表哪支球队”。

## 球员名单录入方式

必须支持至少三种：

### 1. 手工录入
手机端快速增加球员。

### 2. 批量粘贴
支持从微信 / Excel 复制多行文本。

建议格式：

号码 姓名 位置 备注

### 3. 文件导入
必须支持：
- CSV
- XLSX

提供可下载的标准模板。

建议模板字段：
- 球衣号码
- 姓名
- 位置
- 是否门将
- 是否队长
- 出生年份
- 资格状态
- 备注

导入时必须：
- 预览
- 显示错误行
- 提示重复号码 / 重复球员
- 用户确认后才正式写入
- 不允许静默覆盖现有球员

## 球员名单打印 / 导出

每支球队必须可以生成“正式参赛名单”。

至少支持：
- 浏览器直接打印
- A4 版式
- PDF 打印
- CSV / XLSX 导出

打印版至少包含：
- 赛事名称
- 球队名称
- 队徽（如有）
- 球员号码
- 姓名
- 位置
- 门将
- 队长
- 资格状态
- 领队 / 教练
- 打印日期
- 签字区域（领队 / 赛事管理员）

手机端点击：
“打印 / 导出名单”

即可生成适合 A4 的页面。

注意：
公开打印版不要包含身份证号、电话等敏感信息。

验收：
- 一支队录入 20 名球员
- 手动录入成功
- 批量粘贴成功
- XLSX 导入成功
- CSV 导入成功
- 错误行不会污染现有数据
- 导入预览可取消
- A4 打印正常
- 导出再导入不丢数据
- 修改球衣号码不改变 player_id

# M3 — 本场名单与比赛事件

## 本场名单
每场比赛双方都可以选择：
- 首发
- 替补
- 门将
- 队长

比赛开始后默认锁定。

管理员强制修改：
- 必须记录原因
- 必须进入操作日志

## 比赛事件
至少支持：
- 进球
- 助攻
- 黄牌
- 红牌
- 两黄变红
- 换人
- 点球
- 乌龙球
- MVP

事件必须关联 player_id，不得只保存姓名或号码。

示例：
12' 黄牌 · #8 阿迪力
24' 进球 · #10 阿尔曼
31' 换人 · #7 ↓ / #18 ↑

同一份事件数据未来供：
- EVENT 比赛报告
- BROADCAST
- 射手榜
- 纪律
- PLAYER

验收：
- 球员改号后历史事件仍正确
- 删除球员时已有历史事件不得断链
- 比赛结束后时间线完整

# 当前阶段完成标准

当前第一阶段只有在以下全部通过后才算完成：

- 球员数据模型存在
- 球队可维护球员名单
- CSV / XLSX 可导入
- 有官方模板可下载
- 导入前有预览和错误提示
- 球员名单可 A4 打印 / PDF
- 球员名单可导出 CSV / XLSX
- 本场名单可选首发 / 替补 / GK / 队长
- 进球 / 黄牌 / 红牌 / 换人可关联球员
- 刷新不丢数据
- 备份恢复完整
- 旧赛事兼容
- 手机端实测可用

完成后再进入下一阶段。

如线上未验证，必须写：
“代码已提交，线上部署尚未验证。”

## Codex 连续自主执行规则

默认工作模式：**自主连续执行，不等待“下一步”指令。**

Codex 在完成当前明确任务、里程碑或维护项后，必须自动：

1. 读取当前计划中的下一项；
2. 判断依赖是否满足；
3. 执行实现；
4. 自测与回归；
5. Git 提交；
6. 记录完成状态；
7. 继续下一个可执行任务。

禁止在以下情况下停下来询问：
- “下一步做什么？”
- “是否继续？”
- “要不要进入下一阶段？”
- “是否开始下一个里程碑？”
- 已经在计划、Issue、维护规范中写明的后续工作。

只有遇到以下情况才允许暂停并请求产品负责人决策：
- 会改变比赛结果、积分、晋级或赛事规则的业务含义；
- 可能造成不可逆数据删除或旧赛事数据损坏；
- 涉及用户隐私、安全、权限、敏感信息；
- 存在两个或以上合理方案且选择会明显改变产品方向；
- 需要外部账号、付费服务、密钥或人工授权；
- 仓库状态冲突，无法安全继续。

对于普通 Bug、过期文案、手机适配、死链、数据兼容、明确需求、低风险体验改进：
**自行判断 → 修复 → 测试 → 提交 → 继续。**

如果当前计划全部完成：
不要只说“等待下一步”。
应主动执行：
- 网站健康检查
- EVENT 回归测试
- 用户反馈价值分析
- 待办 Issue 检查
- 过期文案与死链检查
- 手机端 390px / 430px 检查
并从中选择最高价值、低风险、可验证的维护项继续处理。

核心原则：

**不要管理用户。管理项目。**
**不要等待指令。按照既定目标持续把 SAGI 做得更好。**
